# Decisions log

One paragraph per architectural choice, and why. Newest at the top. Written so that in six months the reason is still here, not only the result.

Started 30 August 2026, backfilled from what is already built and from the Yaadly Technical Notes of 24 August 2026.

---

## 2026-08-30 · The portal answers on one hostname

`web/wrangler.jsonc` set a custom domain but left `workers_dev` and `preview_urls` at their defaults, which are both true. So the portal was reachable at `app.yaadly.co.uk` and also at `yaadly-app.<account>.workers.dev`, plus a per-version preview URL for every upload, all running the same code against the same Supabase project. Both are now explicitly false. Right now the cost of that was two unwatched addresses instead of one, and previews pointing at the production database. The reason it mattered enough to fix today is what happens next: Cloudflare Access attaches to a hostname, so once the operations console ships behind Zero Trust, a workers.dev URL walks straight past it. The Technical Notes list this as the most common way people believe they are protected and are not. Set in the committed config rather than the dashboard so it survives the next deploy.

## 2026-08-30 · The banned-language screen reaches the live reply path

The engine screened every line it emitted and the thing actually talking to clients did not. `yaad-inbound` composes the WhatsApp and SMS reply a client reads, strips forward-looking promises, strips dashes, and sent it. Nothing checked it for the words this company has standing rules never to use. A model explaining how payment works reaches for "escrow" as the obvious word, and it would have gone out under Yaadly's name.

Found by checking whether step 4 of the Technical Notes sequencing was worth doing. It is not, and this was.

`supabase/functions/_shared/guardrails.ts` is a direct port of `BANNED_TERMS` from `yaad/guardrails.py`. It goes in `twiml()`, which is the single place anything in that function reaches a person, so the fixed strings are screened alongside the model-written ones: it costs nothing and a careless edit to a fixed string cannot walk past the rule either.

On a hit the behaviour differs from the engine on purpose. The engine raises, which is right for a batch job and wrong here, because raising means somebody who messaged about their roof gets silence and silence is indistinguishable from the message vanishing. Instead the client gets a short holding reply, the draft goes to the function log, which is private to the project rather than to a third party, and a phone alert says a reply was held back. The alert carries the guidance strings only, never the draft, because ntfy is a public service and the draft is model prose about somebody's property. That is the governing rule doing what it is for: the machine refuses to send it and hands it to a person.

`yaad-completion` and `yaad-kickoff` now flag the same list rather than blocking it, because a human reads those before anything is issued. The human gate was already there; what was missing was telling them. `yaad-whatsapp-webhook` needed nothing: its replies are fixed templates and a deterministic status read-back, and its model call only fills a job card.

Ten Deno tests, wired into CI. Seven assert the screen, using the same five phrases the Python suite uses so a loosened pattern turns one of the two red. Three assert the gate is still wired into `yaad-inbound` and the two draft producers, because the realistic failure here is not a broken regex, it is somebody removing the call in good faith while tidying the reply path.

## 2026-08-30 · MiniMax stays for now, and the switch is triggered by real data

Amends the entry below, same day. The destination is settled and the plumbing is built; the timing is not now. Founder decision: keep running on MiniMax while the data flowing through these functions is synthetic. That is consistent with the Technical Notes, which said MiniMax is fine for the buildathon with synthetic data and that the move belongs before the pilot. The trigger is therefore not a date but a fact: **real client and worker data, which arrives with the December pilot in Kingston and Portmore.** On cost, for the record, because it was asked and answered rather than assumed: Mistral Large is about 1.7 times MiniMax per token, which at pilot volume is roughly one pound a month, so cost is not what is deciding this either way.

One thing changed in the code as a result. The MiniMax branch was written as a loud temporary fallback that logged a warning on every single call saying the migration was incomplete. Now that running on MiniMax is the deliberate current state rather than an unfinished job, that warning would fire thousands of times against a decision somebody already took, and an alarm people are trained to ignore has stopped being an alarm. It is gone. What remains is the honest signal: `yaadly.model.region` rides on every model span, silent when nobody is asking and conclusive when they are. The day the answer has to be `eu`, one query proves it.

## 2026-08-30 · The text model moves to the EU, and the provider stops being eight constants

Founder decision: move off MiniMax to an EU endpoint before the pilot carries real data, and Mistral is the endpoint. The reason is jurisdictional rather than technical. MiniMax is hosted in China, it was hard-coded into eight live Edge Functions as a pair of constants each, and everything a client typed and everything a worker said over WhatsApp passed through it. China has no UK adequacy decision, and Jamaica's Data Protection Act 2020 restricts transfers where the destination lacks adequate protection. Mistral because it is EU hosted, it speaks the OpenAI chat completions shape so the eight call sites barely changed, and it offers a signed DPA.

The shape matters as much as the destination. The provider now lives in `supabase/functions/_shared/textmodel.ts` and nowhere else, so it is a decision in one file rather than a property of eight, and a future move is a secret change rather than a deploy. Four `TEXT_MODEL_*` secrets override everything, which is the escape hatch that stops the next migration being another eight-file edit. CI enforces it two ways: the shared-copy check now loops over every file in `_shared` rather than naming `otel.ts`, and a new job fails the build if any function hard-codes a model endpoint again.

The MiniMax branch is still in the resolver, deliberately and temporarily, so that deploying this could not take the intake flow down before the Mistral secret exists. It is a noisy fallback rather than a quiet one: it logs a warning every time it runs, and `yaadly.model.region` travels on every model span so the question "is this still going to China" is answered from telemetry rather than from memory. `RUNBOOK.md` step 9 is the three-step completion, ending in deleting that branch. A fallback to China that nobody notices is exactly how a migration gets declared finished and is not.

## 2026-08-30 · Identity documents are withheld from the model entirely

Supersedes the entry below it, same day. Founder decision: stop sending the government photo ID, the live selfie and the face video to NVIDIA, keep the machine read for everything else. Persona already does the identity step with real document-authenticity and liveness checks, so the second copy of a passport in a US model vendor's request logs was adding a transfer of the most sensitive thing on the file without adding a check anybody relied on. The consent gate made it lawful to ask for. It did not make it worth asking for. Implemented as `IDENTITY_DOCS` in `yaad-vetting-review`, tested before the mime check and before the download so the file is never fetched from the bucket on that path, with no override flag and no query parameter. The face-match pass went with it. Where Persona has passed, that comparison happened somewhere stronger; where Persona has not, the review now states in plain words that nobody has compared the two faces, which is a better outcome than a model guessing. Withheld documents stay on the skipped list with the reason, because a document that vanishes from the review reads as a document that does not exist, and the count goes to telemetry so it is provable after the fact rather than promised. Applicant-facing copy in `JoinFlow.tsx` updated and `AI_CONSENT_VERSION` bumped to `ai-review-v2`; v2 is strictly narrower than v1, so existing consents still cover what is done, but the sentence changed and a consent is tied to its sentence.

## 2026-08-30 · Identity documents go to a model, with consent, to one vendor

Recorded because the first draft of `CLAUDE.md` carried a flat rule that ID documents never reach a model API, which is not what is built and would have had a future session delete a working feature. What is actually built: `yaad-vetting-review` sends identity documents to NVIDIA's hosted vision model, one image per call, so the desk has a machine reading before a person opens the file. It never decides; there is no code path in it that approves or declines. It runs only when `ai_review_consent` is `granted`, NULL counts as declined, and the gate sits inside the review function rather than at the caller so the desk's re-run button cannot override the applicant's refusal. That is the right shape. The open item is not the consent gate, it is the destination: NVIDIA hosted means a transfer of identity documents to a third country, which is exactly the processing a DPIA has to cover and exactly the reason the OIC registration matters. Same class of question as the engine's model provider, and it should be answered at the same time.

## 2026-08-30 · One repository, not three

The Technical Notes recommend three repositories: a private Python engine, a private TypeScript product monorepo, and a public static landing page. Today this is one repository with the same separation inside it: `yaad/` and `tests/` are the engine, `web/` is the Next.js app, `supabase/` holds the Edge Functions and migrations, `docs/` is the static marketing site on GitHub Pages. The separations the notes were actually protecting are already in force. The marketing site has no build step and deploys independently, so a broken app build cannot take `yaadly.co.uk` down during a launch window, which was the main point. Splitting the repositories now would cost a week and buy visibility control, which is a separate decision (see below). Revisit if repository visibility forces it, or if a second engineer joins.

## 2026-08-30 · The engine stays Python

The Technical Notes reversed an earlier suggestion to port the engine to TypeScript, and the reversal is right. The tests are the asset: they are what proves the AI never releases money, rules a dispute or moves a Yaad Score. A rewrite risks losing coverage exactly where coverage matters and gains nothing a judge, a client or an investor can see. Python is also the better home for what is on the roadmap, EXIF parsing and image checks on evidence photos, and the hiring pool for LLM orchestration and WhatsApp Business API work skews Python anyway. Treat a rewrite as a 2027 decision, to be made only if a TypeScript-first engineer joins and the split becomes a real burden, and then with the tests as the specification.

## 2026-08-30 · The engine stays stateless

Job Card in, structured result out. No database access, no auth, no session state. Everything stateful lives in Postgres. This is the boundary that makes a two-language codebase cheap instead of painful, and the agents were already written this way, so it costs nothing to hold. It is also what would let the engine be wrapped in a thin API and deployed separately later without disturbing the agents or the tests.

## 2026-08-30 · Pricing is a lookup and a model call must never be added to that path

Recorded here as well as in `CLAUDE.md` because it is the single most likely thing for a future agent to helpfully break. The founding premise is that a client in London pays what a client in Portmore pays. A hallucinated price band breaks exactly the thing the business exists to fix, so pricing reads from researched benchmarks in `yaad/benchmarks.py` and returns "no public price exists in Jamaica for this work" rather than a guess. That answer is correct and complete, not a gap. Widening coverage means adding a sourced benchmark row.

## 2026-08-30 · The worker web surface stays thin

The diaspora client is motivated, on a laptop, and will tolerate friction. The worker in Portmore is on a phone, mid-job, and will abandon anything that is not WhatsApp. So the worker portal exists for the two things WhatsApp does badly, structured onboarding with credentials and file upload, and for nothing else. Building a full worker dashboard for December would be wasted effort because it will not be opened. The consequence worth watching: if the worker journey is WhatsApp-first, ID documents land in Meta's infrastructure before they reach ours, which is why identity verification links out to a vendor flow rather than accepting documents over the chat.

## 2026-08-30 · Model provider is a configuration value, and the current one has to change before real data

The engine speaks the OpenAI chat completions API, so any compatible endpoint works from two environment variables. That was a day-one call made because the buildathon gateway key had not been issued when the build started, and it turns out to be worth much more than the convenience. MiniMax is a Chinese provider and is fine for the buildathon with synthetic data, which is what synthetic data is for. Once real job data flows, worker names, property addresses, job details, voice transcripts, that becomes a transfer of personal data to a third country, and two regimes bite: UK GDPR, which needs adequacy or appropriate safeguards and has neither straightforwardly available for China, and Jamaica's Data Protection Act 2020, which restricts transfers where the destination lacks adequate protection. For the pilot, move to a provider with a UK or EU region and a signed DPA. Because of the day-one design that is a config change, not a rewrite.

## 2026-08-30 · Data protection registration is the item most likely to stop the launch

Not a technical decision, recorded here because it constrains the technical ones. Jamaica's Office of the Information Commissioner requires registration before processing personal data about people in Jamaica, and the workers put a UK company in scope regardless of where it is incorporated. Operating unregistered is a criminal offence; enforcement has not been switched on, which is a grace period rather than an exemption. Separately, UK GDPR requires a DPIA for high-risk processing, and collecting ID documents about individuals across two jurisdictions is high risk by any reading. Neither is difficult, both take longer than expected, and both tend to be discovered in November. This also needs a qualified solicitor in both jurisdictions before any real payment is taken. Timing is Monique's.

## 2026-08-30 · Guardrails live in code and in tests, not in prompts

`yaad/guardrails.py` screens outbound text for banned language and refuses any money or reputation action that does not carry a named human decider. The tests prove it. The reason this is in code rather than in a system prompt is that a model can be talked past a prompt and cannot be talked past a raise. The layer still missing is the third one the Technical Notes recommend: a database-level constraint that refuses a payment release without a named human recorded. Application code is what an agent writes; a database rule is set up once and then left alone, and it holds even when the code above it is wrong. Worth adding before any payment path exists, which means before the December pilot takes money.

## 2026-08-26 · DNS on Cloudflare, app and site on separate hostnames

The `yaadly.co.uk` zone went active on Cloudflare on 26 August 2026. The marketing site serves from GitHub Pages at the apex, and the Next.js app deploys as a Cloudflare Worker at `app.yaadly.co.uk` via OpenNext. Two hostnames, two deployment paths, one of which has no build step. When the operations console arrives it gets its own hostname for the same reason plus one more: a separate hostname is what allows Cloudflare Zero Trust to sit in front of it, and the console holds ID documents and payment controls. That subdomain must be proxied, orange cloud rather than grey. ## The client funnel lives in the app, and takes no account (Stage 2, 30 Aug 2026)

Stage 1 deleted the post-a-job funnel from `docs/index.html` so the marketing site could be short. The plan said to leave the old path working until the app funnel existed. It did not: the app's `/jobs` is a BOARD, a list of other people's jobs, and nothing in `web/` ever created one. So for a window there was no way to post a job anywhere, and the app's own "Post a job" button pointed at `yaadly.co.uk/#post`, which redirected to the board. A client went in a circle.

`web/app/jobs/new` is the funnel, and it is now the only place a job is created.

**No account, and no password on the page.** Founder decision, 30 August: no account to get quotes, an account once a job is booked. The account is worth something at booking, where it approves evidence, holds the invoice and carries the property record between jobs. In front of a quote it is a toll gate on the way in.

**Two backends, both already hardened, neither changed.** The work goes to `yaad-post-job` in draft mode, which writes a job at `stage 0, open false` and deliberately stores no personal data. The contact details go to `yaad-enquiry`, which has the per-recipient throttle, the receipt tracking and an honest answer for somebody who gave a phone number rather than an email. The enquiry carries the job reference so the desk reads them as one thing. No new table.

**Three behaviours carried over on purpose**, because a rewrite is the easiest place to lose them: the job saves as a draft before a single personal detail is asked; the contact field still says "Hidden from workers until you start a chat with one. You control when it's shared."; and the reply promise is one working day.

**The end state names what happens next.** "Your job is saved" tells somebody who has just described water running down their mother's bedroom wall nothing at all. It now says a person reads it within one working day, then an itemised quote with labour split from materials, then a written scope, then evidence at every stage with nobody paid for a stage until it is approved, and that no account is needed until they book.

`TRADES` and `PARISHES` moved to `web/lib/taxonomy.ts`. They were declared inside `JoinFlow.tsx` and the funnel needs the same two lists. Two copies drift, and the day they drift a client posts a job in a trade no worker profile can carry.

## Quotes without an account, and the booking that needs one (Stage 2.2, 31 Aug 2026)

The decision was "no account to get quotes, an account once a job is booked." Half of it was not true: `job_quotes` was only ever rendered inside the portal, which is behind auth, so a client had to make an account before seeing a single price.

**Looking is open, choosing is not.** `quotes_for_code` and `job_for_code` are security-definer functions taking the job id and its `portal_code`, which is the bearer token the WhatsApp link and the portal claim already ride on. They return what a client needs in order to choose and nothing else: no client contact details, no address. `/jobs/[id]/quotes?code=` renders them for an anonymous visitor, labour split from materials, materials marked at cost.

**Accepting is the booking, and the booking is where the account appears.** `accept_quote_as_me` is authenticated only and refuses any caller who is not that job's `client_email`. So holding the link is enough to look at prices and never enough to book one. Pressing Book with no account routes to `/portal/join` carrying the job, the code and the chosen quote; the account is made there and the quote is accepted on the way back.

**A job that already has a worker is not re-bookable through it.** Changing a worker mid-job is a desk decision with a conversation behind it, not a button.

**Found while testing:** `revoke all ... from public` did not take execute away from `anon`, because `anon` is a role with its own grant rather than a member of PUBLIC for this purpose. `accept_quote_as_me` was therefore callable by anonymous visitors. The body already refused them, having no email in the JWT, so nothing could be booked, but a booking function anonymous callers may call is one bug away from one they may use. `anon` is now revoked by name.

**Not built:** nothing tells the client a quote has landed. The page is honest when empty and the link keeps working, but the client has to come back and look. Notifying them is its own piece of work and needs the WhatsApp credentials that are still unset.


## Clients sign in with a code, not a password (31 Aug 2026)

The audience is diaspora clients, often older, often on a phone in another country, who have already explained the whole job once. "Choose a password, at least 8 characters" is where those people stop, and it bought nothing: the job code was always the real gate and a password was a second secret to lose on top of it.

`yaad-portal-code` issues a six digit code and delivers it by email through Resend, and by WhatsApp or SMS through Twilio when the job carries a number. It uses `generateLink`, which returns both a link and a six digit `email_otp` for the same token, and takes the digits. That was chosen over Supabase's own magic-link mail for three reasons: a link opened in a different browser than the one it started in is the classic way magic links strand somebody, digits travel over WhatsApp as easily as email, and GoTrue's templates stay untouched.

The function issues and delivers and nothing else. It never sees the code come back and never mints a session; verification happens in the browser against Supabase directly, so the code goes to the mailbox or the phone and nowhere else, which is the only reason holding it proves anything.

**The gate is unchanged.** A new client still presents a job code and `pend_portal_code` still rules on it, rate limited on both the email and the code. A returning client is never asked for one, because locking somebody out of their own history over a code from months ago is the wrong trade. `email_has_account` decides which case it is, and it is granted to nobody: callable only with the service role, because "is this person a Yaadly client" is the question an account enumeration attack asks.

**`verifyOtp` takes type `"email"`, and this is measured rather than assumed.** The founder signed in through the page on 30 August and the auth log shows a single `POST /verify` returning 200 with `login_method: "otp"`, `provider: "email"`. Write that down, because the storage says otherwise: `generateLink` files the token in GoTrue's `recovery_token` slot and logs the event as `user_recovery_requested`. It still verifies as `email`. It also cannot be rediscovered by probing, since GoTrue returns the identical "Token has expired or is invalid" for all four types when the token does not match, so a wrong type looks exactly like a wrong code.

Existing accounts keep their passwords. Nothing was removed from them; they simply have a way in that needs nothing remembered.

## One door in (Stage 3, 31 Aug 2026)

The plan said to retire `yaad-post-job`. That would have broken the funnel, because `/jobs/new` calls it in draft mode, which is the right thing to call: it is rate limited, it writes `stage 0, open false`, and it deliberately stores no personal data. What actually needed retiring was narrower and more important.

**`yaad-post-job`'s `golive` mode is gone.** It created an account from a password, captured the Client Guidelines signature and opened the job, and it was step 6 of the five-step funnel deleted in Stage 1. Nothing had called it since. Removing it was not tidying: it was a **second account-creation path that took a password**, on a journey that moved to a six digit code with no password anywhere. A dead endpoint that can still mint password accounts is exactly the kind of thing that quietly outlives the decision to stop doing it. `verifyPassword`, `signedInUser` and `MIN_PASSWORD` went with it, forty-seven lines of password handling. It answers 410 and names where each part went.

**`yaad-website-intake` is retired to a 410 stub.** It served the public "Tell us what needs doing" form deleted in Stage 1, took no authentication by design, and created jobs. The only reference left anywhere was one line in `web/README.md`. It is a stub rather than a deletion because an unreferenced public endpoint that writes rows is precisely what survives three refactors unnoticed, and a 410 that says what happened beats a 404 that says nothing. If something out there still calls it, that is now visible rather than silent.

**One stale link found and fixed:** the portal's `ServiceNext` still sent clients to `yaadly.co.uk/#post`, the deleted funnel, and to `#services`, which moved to its own page in Stage 1.

**What can create a job now:** `/jobs/new` through `yaad-post-job` draft mode, plus the WhatsApp webhook and `yaad-inbound` for email and SMS. Those are channels rather than rival funnels: they land in the same tables with the same portal code model, which is what the plan meant by one code path plus WhatsApp intake.

## The ID check must not exclude the people it is for (31 Aug 2026)

Persona's template decides which government documents it accepts, and **most Jamaican tradespeople do not hold a passport**. A passport-only template would silently exclude the supply side this business is built on, and would do it in a way that looks like ordinary rejection.

**The Persona API does not expose enabled ID classes.** Checked directly: the template config it returns carries Persona's generic field schema, not the document types the template accepts. So this cannot be verified, changed or monitored from code. It is a dashboard setting and the runbook says which documents to enable.

**So the product does not depend on it being right.** A worker can press "It would not take my ID. Let me send it another way." on the ID step, which switches to the in-page capture and upload for a person to check by hand. The existing fallback only fired when Persona failed to LOAD, so somebody whose voter card was refused saw Persona work perfectly and turn them away with nowhere to go. The escape is theirs to take rather than something they must ask for, the copy names the voter card and the driver's licence, and it says plainly that it does not count against them.

**The thirty second introduction** is Phase 2's, optional, and the only thing on that page a client ever sees. It is held to the same rule as the identity captures: a face and a voice is the same category of thing as a selfie whatever it is called, so `intro_video` is on `IDENTITY_DOCS` in `yaad-vetting-review` and is never sent to a model.

## The approve button, and the trigger that had to be found first (Stage 5.1/5.2, 31 Aug 2026)

The evidence ledger has said "Money moves when you approve them" since 30 Aug. It was wired to `jobs.status = 'evidence'`, a value the `jobs_status_check` constraint has never allowed, so `awaitingApproval` was always false and the sentence had described nothing since the day it was written.

**Two pieces were needed for the sentence to become real, not one.** Something has to put the job into a state where there is genuinely something to approve, and something has to let the client say yes.

`'evidence'` joins the allowed status values. `sync_job_status()`, the existing trigger that recomputes `jobs.status` from scratch on every write, gained one more fact: when a job has a worker and the stage currently being worked has evidence filed against it with no `stage_approvals` row yet, status is `evidence` rather than `in_progress`.

**The first version of this used a second trigger to set the status directly, and it silently did nothing.** `sync_job_status` already owned that column and ran after mine on the same statement, recomputing it from its own rules and overwriting what I had just set. Two triggers deciding one column is exactly the shape that reads correctly and does nothing, and it was only found by testing the actual database rather than reading the code. Fixed by giving the one existing authority the missing fact rather than adding a second one beside it. The evidence-side trigger now only pokes the job row so the recompute fires; it does not decide anything itself.

`approve_stage(p_job)` is authenticated only, same access rule as `client_go_live`: `revoke ... from public, anon` named explicitly, because Supabase grants `anon` execute on every function in an exposed schema and revoking from `public` alone leaves that standing, the same trap this repository has hit twice before (20260828b, 20260828f). It refuses a caller who is not the job's client, refuses while a dispute is open (`state <> 'resolved'`, the same predicate the dispute RLS policies already use), refuses when nothing has been filed for the stage, and on success snapshots every evidence item's id, sha256 and label into `stage_approvals` before advancing `jobs.stage`.

It does not decide a job is complete. Proving one stage is a smaller claim than finishing the job, and nothing currently marks a job `complete` at all; that is a separate, later piece of work.

**Exposed once**, in `EvidenceLedger`, as a one-tap button for the client only, beside a real link to the dispute form (`?tab=job#dispute`) rather than a second copy of it. Stage 6's WhatsApp approval reply calls the same `approve_stage()` function; nothing about this design assumed a browser.

**A second bug found by clicking rather than reading:** the ledger's headline said "Nothing filed yet" in the same breath it listed two filed items and showed the Approve button, because `currentStage === 0` was checked before `awaitingApproval`. Whether something is waiting on a human is the more urgent fact. Fixed by reordering the two checks.

Verified against the live database with real auth tokens, not reasoning alone: the right client approves and the stage advances with a fingerprinted record; the wrong user is refused; an open dispute refuses and a resolved one un-blocks; a stage with nothing filed is refused; an anonymous caller is refused at the grant level, before the function body runs; `stage_approvals` is readable by both parties to the job and by nobody else. Then walked through the real browser UI with a forged but genuine Supabase session: the button rendered, the tap advanced the stage rail from "Stage 1 on site" to "Stage 1 released," and the button correctly disappeared once there was nothing left to approve.

## The materials store gate, loosened to when it actually applies (Stage 5.4, 31 Aug 2026)

Founder's own wording: "say where materials are kept" becomes a go-live condition only when the accepted quote includes materials; small jobs default to worker supplies. Before this, `enforce_store_before_open()` blocked every job from opening until the client named a materials store, whatever the job needed: a two hour call-out with nothing to buy was held up by a question that did not apply to it.

`materials_store_nominated(p_job)` now returns true outright when the job has no *accepted* quote with `materials_jmd > 0`, and only falls back to the original rule (a real place named, or the explicit "none available" answer) when there is one. One function decides this, and both callers, the `enforce_store_before_open` trigger and `client_go_live`'s own `WHERE` clause, inherit the change for free.

**Reading `client_go_live()` closely turned up something worth recording:** it opens a job only when `worker_email` is empty, meaning a job always goes live *before* any quote is accepted. No job can have an accepted quote at the moment this gate is checked. So the loosened rule does not merely soften the block for small jobs, it removes it from the go-live moment entirely; the question genuinely belongs later, once a quote naming materials has been chosen, which is a state that only exists on the job room page after the fact.

**The client-facing checklist (`jobGates`) had to move with it, or it would show a question the database no longer requires an answer to.** It now takes `hasAcceptedMaterials` and only lists "Say where materials are kept" when that is true. On the pre-go-live "still waiting" list it is always `false`, correctly, since no job on that list can have an accepted quote by construction. On the job room page it is computed from the real quotes already loaded on that page: `status === 'accepted' && materials_jmd > 0`, the same test the database uses.

The separate trigger that blocks *filing materials evidence* without a named store is untouched: once materials are actually involved, that check still applies at the point it always applied, and my change does not reach it.

Verified directly against `materials_store_nominated()`: a job with no accepted quote passes with no store named; a job with an accepted quote carrying materials is refused until one is named; naming a lockable store with a description clears it. Test rows deleted.

## The client hears about every state change, not just the quote (Stage 5.3, 31 Aug 2026)

Before this, exactly one event ever reached a client: a price landing, fired from `web/app/jobs/actions.ts` right after `submitQuote` inserted the quote. Evidence landing, a stage being released, a dispute being raised, none of those said anything. The founder's own instruction was to fire from the same functions that change state, never from the UI, and to build the notification system beyond the "worker on site today" case, which has no schema signal to hang off (see below).

**One edge function, one shared secret, four kinds.** `yaad-notify-client` replaces the single-purpose `yaad-quote-landed`. The caller sends `{secret, jobId, kind}` and never a message body: all wording is composed inside the function from a fixed `kind` enum (`quote_arrived`, `evidence_landed`, `dispute_raised`, `stage_released`). A leaked secret can trigger a real notification about a real job state; it cannot make the system say arbitrary things to a real phone number. The same shared-secret-hash pattern already used for the deletion-clock cron job (`20260827f_the_deletion_clock_actually_runs.sql`) is reused here: a random secret generated once, only its SHA-256 hash kept in `app_settings`, the plaintext baked into the trigger function bodies.

**Three triggers, not one function called from three places.** `notify_client_quote_arrived()` on `job_quotes` AFTER INSERT WHEN `status = 'submitted'`. `notify_client_on_job_change()` on `jobs` AFTER UPDATE, covering both `evidence_landed` (status flips to `evidence`) and `stage_released` (stage advances) in one function, because both are facts about the same row changing on the same statement. `notify_client_dispute_raised()` on `disputes` AFTER INSERT, unconditional: every dispute notifies the client, framed as a receipt rather than an accusation.

**`submitQuote` no longer calls a notifier at all.** The UI-fired call was removed outright rather than left alongside the trigger, because a state change firing twice from two places is exactly the kind of drift this plan exists to close off. `yaad-quote-landed` is retired to a 410 stub, same shape as `yaad-website-intake`: it read a client's contact details on the caller's bearer token, so an unreferenced version of it should say what happened rather than 404 silently.

**A bug the plan's own honesty requirement caught: the very first approval on any job never notified.** `notify_client_on_job_change()`'s `stage_released` condition originally checked `stage_approvals.stage = old.stage`. `approve_stage()` clamps a job's very first stage to 1 internally (`greatest(jobs.stage, 1)`) while `jobs.stage` itself is still sitting at 0 going in, so the approved row lands as `stage_approvals.stage = 1` while `old.stage` was `0`. They never matched, so the first stage release on every job, the exact moment the product is named after, stayed silent. Confirmed live before fixing: `approve_stage` on a test job moved `jobs.stage` 1→2 and inserted `stage_approvals.stage = 1`, and `net._http_response` recorded no third call. Fixed in `20260831j` by keying off `new.stage - 1`, which is always the stage that was just approved regardless of where `jobs.stage` started, rather than `old.stage`. Re-tested live: fires correctly now, on the first stage and on later ones.

**Honest answer on "worker on site today," not a hedge.** There is no Arrival Log table and no column anywhere that records a worker checking in. Nothing in this migration invents one. This notification stays unbuilt, not deferred behind a vague "would need to check": it needs a real arrival event to fire from, which is its own piece of schema work, not a wording change to this file.

**No spam confirmed live, not assumed.** A second evidence insert against a stage that has already flipped `jobs.status` to `evidence` does not fire a second `evidence_landed`, because the trigger's `WHEN` clause is `old.status IS DISTINCT FROM 'evidence' AND new.status = 'evidence'`, a transition, not a state. Verified by inserting two evidence rows for the same stage and checking `net._http_response` stayed at one new row, not two.

**Verified against the live database with real HTTP calls, not migration success alone.** All four kinds fired and returned `{"ok":true,"told":true}` from `net._http_response`, including the `stage_released` fix, exercised through a real signed-in session (password-grant login, not a service-role call) calling `approve_stage` for real. Test job, test users and test identities deleted after.

## Worker video evidence, and an offline queue with nothing to reuse (Stage 5.5, 31 Aug 2026)

Photo evidence has worked since 27 Aug, but only photos: `evidence-actions.ts` runs as a Next.js Server Action, and a video is too large to ride inside one. The plan called for reusing the resumable-token pattern from the application flow (`yaad-vetting-upload`). What that meant in practice needed adapting, not copying: vetting invented a token because an applicant has no account yet. A worker filing evidence already has a real account and a real session, and `public.evidence` plus the evidence storage bucket already carry RLS that lets a job's own worker or client read and write exactly their own job's folder (20260827a, 20260830b). Inventing a second credential on top of that would have been a parallel authorisation system answering a question RLS already answers.

**`yaad-evidence-video` runs entirely as the caller, never as service role.** Every storage and database call inside it uses a Supabase client built from the caller's own bearer token, so Postgres RLS is the only authorisation check that exists. A worker who is not on a job gets refused by the same policies that would refuse them calling supabase-js from a browser console; the function repeats none of that logic itself. This is the actual reuse the plan called for: the vetting flow's start-PUT-finish shape (the server picks the path, mints a one-path signed URL, the browser PUTs straight to Storage, the server verifies and hashes what arrived before writing the row), carried over with the credential swapped for the one that already exists here. The row-write step is the one invariant that could not be relaxed: `evidence-actions.ts`'s own rule, "computed HERE, on the server, from the exact bytes stored," applies to a video exactly as it does to a photo, so `finish` downloads what Storage actually holds and hashes that, never a client-reported figure.

**80MB, not the bucket's 500MB.** The function has to hold the whole file in memory to hash it, on the same free-plan edge runtime `yaad-vetting-upload` already uses for its own 50MB video cap. 80MB is a few minutes of ordinary phone video at a reasonable bitrate, comfortably clear of the bucket's ceiling, and it leaves headroom for the runtime itself rather than chasing the largest number the bucket happens to allow.

**The offline queue is new, not reused.** Nothing in this repository did anything like it before this. IndexedDB holds each queued video as a Blob with its label, stage and kind, because it is the only browser storage that can hold something video-sized without choking, and a queued item survives a dropped connection, a closed tab, or a phone that locks mid-shoot. Upload is sequential, one item at a time, deliberately: a worker on a weak signal filing two stage videos should not have them competing for the same thin pipe. Retry is whole-file, not byte-range resume; nothing here does chunked resume, Supabase Storage's own tus support included, and adding it for a pilot of a handful of jobs a week was not this stage's job. A failed item retries itself automatically on reconnect up to five times, then waits for a worker to tap Try again, so a video that is failing for a real reason (the materials store question, most likely) does not silently hammer a weak connection forever.

**The materials-store gate needed nothing extra.** The finish step inserts into `public.evidence` exactly as `evidence-actions.ts` does, so `evidence_materials_needs_store()` (20260828c) fires the same way and with the same message whether the evidence arrived as a photo or a video. One gate, one trigger, both upload paths.

**A bug caught before it was ever live: `functions.invoke` hides a refusal's real message.** A non-2xx response from an edge function arrives from `supabase-js` as an `error` object with the JSON body sitting on `.context`, not on `data`. The first draft read `data?.error`, which is `undefined` on every refusal, since every refusal in `yaad-evidence-video` is a non-2xx status. That would have shown a generic "Could not start the upload" for every real reason a worker needed to hear, including "You may not be on this job" and the materials-store message. `JoinFlow.tsx`'s own `call()` helper for `yaad-vetting-upload` already carries the fix, written for the identical problem; `video-upload.ts` copies it rather than rediscovering it.

**Video-only, worker-only, by design.** The photo form stays exactly as it was, open to both client and worker, unchanged: that question was never Stage 5.5's to answer. The video form renders only for `role === "worker"`, matching the plan's own wording ("worker video evidence upload") even though RLS itself would not object to a client using it.

Verified against the live database and a real browser session, not curl alone: `start` refuses a worker who is not on the job, refuses no bearer token at all, refuses an oversized file, refuses a non-video mime; `finish` writes a row whose `sha256` was independently reproduced from the same bytes with a plain `shasum`, matching exactly. Then driven through the actual portal UI as a signed-in worker: chosen video queued, uploaded, the evidence ledger showed it, and `jobs.status` flipped to `evidence`, the same transition Stage 5.3's notifier fires on. Test job, users and storage objects deleted after.

## The worker portal finally shows the money it has promised since it was written (Stage 5.6, 31 Aug 2026)

The worker portal's own header has read "Your work and your money" and its own subhead has promised "what you are owed" since the file was written. Neither was ever true: the page was a plain job list, no figure anywhere, while `jobs.pay_method` and `jobs.pay_ref` sat unused in the schema and unread by any code in the repository, alongside `jobs.owed`, also never written.

**The figure is computed live, not read from `jobs.owed`.** Nothing maintains that column, so trusting it would mean showing null or stale money on a page whose entire point is to be trusted. The same 88%-plus-materials arithmetic `FeeBreakdown.tsx` already shows on a single job is computed here across every job the worker has actually won (an accepted `job_quotes` row), which is the honest source: a job with no accepted quote has no money to show, exactly the guard `FeeBreakdown.tsx` already applies.

**Held and released are a straight read of `jobs.status`, the same binary the job room page's own tile already uses (`held: job.status !== "complete"`).** No per-stage proration was invented: nothing in this codebase splits a labour price across stages today, and building that math for the first time here, unasked, would have been exactly the kind of premature abstraction this repository's own house rule warns against. A job either holds its whole figure or releases all of it, matching what the single-job tile has always shown; this page only sums that same fact across every job at once.

**Released is not paid, and the copy says so.** There is no payment integration in this repository and none is planned before the legal review lands (CLAUDE.md 9 and 10). "Released" means Yaadly's part is done: the client approved, the figure is cleared. What actually moves the money is bank transfer, Lynk or remittance, arranged directly between client and worker, off-platform, within the 3 working days the portal's copy already promised. Claiming "Paid" here would be a real payment claim this repository has made structurally impossible to back up.

**`record_pay_info(p_job, p_method, p_ref)` gives the two orphaned columns an actual purpose: the worker's own note of how that off-platform payment happened, not a payment record Yaadly makes or verifies.** Same shape as `approve_stage`: a SECURITY DEFINER function that checks its own caller rather than trusting a write policy, because `jobs` carries no worker-write RLS policy at all today, only admin write plus client/worker read, and this stays that way. One narrow door, exactly the pattern this repository already uses for every other consequential write. `pay_method` is now constrained to the three real options the FAQ already names (bank transfer, Lynk wallet, remittance pick up); two pre-existing rows (`JOB-0002`, `JOB-0003`) carried `''` rather than null from however the column was first added, normalised to null before the constraint landed, the same rule the function itself applies to every write from here on.

**Recording payment info is only offered once a job is released.** Recording how you were paid for money that has not been released yet does not make sense, and the UI does not offer the form early; the underlying function itself carries no such gate, since a worker's own note of a real payment is theirs to make whenever it actually happened, and adding a status check to the database on top of the UI's own restraint would only be a second copy of a rule that belongs in one place.

Verified against the live database and a real signed-in worker session, not code-reading alone: `record_pay_info` refuses an unrecognised method, refuses a job that is not the caller's, refuses no bearer token at all, and succeeds for the worker's own job. Then driven through the actual portal UI: a job held under an accepted quote showed the correct take-home figure with "Held" and no payment form; forcing the same job's stage to 5 (this repository's own definition of complete, from `sync_job_status()`) flipped it to "Released" and surfaced the once-recorded payment info exactly as stored; changing the method and reference through the real form on screen updated both the row and the rendered page. Test job, quote, profile and user deleted after.

## The video walkthrough, completing a description the FAQ has carried since before this repository's schema caught up to it

`jobs.walk_platform`, `walk_link`, `walk_date`, `walk_who`, `walk_notes` and `signoff_method` were added on 23 Aug and never once read or written by any code in this repository. The FAQ has described what they were for the whole time: "At sign-off you can approve from the evidence package, or book a live video walkthrough: the worker walks the whole site with you on WhatsApp video, Google Meet or Zoom, whichever suits you." This gives that sentence an actual path, rather than inventing a competing design: the three platforms, the free-text preferred time, the notes field, all already matched the copy exactly.

**Two sides, two functions, the same shape as `approve_stage`.** `jobs` carries no client-write or worker-write RLS policy at all, only admin write plus client/worker read, and that stays true: `request_walkthrough()` (client) and `confirm_walkthrough()` (worker) are each the one narrow door for their own side, checking their own caller rather than trusting a write policy that does not exist.

**A request never gates the Approve button.** The FAQ's "or" is a client's choice of how to look at the evidence before deciding, not a condition on deciding. `approve_stage()` was not touched and does not read `signoff_method`; a client can request a walkthrough, get no answer for a week, and still approve straight off the evidence at any moment, exactly as before this migration existed.

**A worker cannot schedule a call the client never asked for.** `confirm_walkthrough()` refuses outright unless `signoff_method = 'walkthrough'` already, i.e. unless a request exists. The link is real: the worker pastes whatever Zoom, Meet or WhatsApp link they actually created, arranged the same way everything else in this product is arranged, over WhatsApp between the two of them. Nothing here calls a video API or mints a meeting; that would be exactly the kind of integration this repository's own scope rules warn against adding without being asked.

**A fresh request clears a stale confirmation.** If a client re-requests, whether to change the date or just to try again, any link the worker had already confirmed against the old terms is cleared along with `walk_who`. A worker seeing an old link standing in for a changed request is worse than seeing nothing: they would join a call for a time that no longer holds.

**`clear_walkthrough()` exists because every state this migration adds needed a way out of it**, the same reasoning Stage 4 already applied to a worker a client will not take. Either side can cancel a request or a confirmed call; both request and cancel are honest room for either party to simply change their mind, not a negotiation.

**What this does not do, on purpose.** The FAQ also describes the notes from the call itself being confirmed by the client and landing on the Completion Report; that is a two-sided sign-off workflow of its own and is not built here. `walk_notes` in this migration is only the client's own note at request time, what they want walked through, not a record of what the call actually found. That is a real next piece of work, not a gap papered over with a field that half does the job.

Verified against the live database with two real signed-in sessions, not one, and a full pass through the actual portal UI in a browser as both parties: a worker refused when confirming before any request existed, a stranger refused when requesting on a job that was not theirs, an invalid platform refused on both functions, a confirm refused with no link. Then driven end to end for real: the client requested a Zoom call through the actual form on screen, the worker saw the request and confirmed a real link through their own form, and both the client and worker views correctly showed the confirmed call with a working join link. Test job and both users deleted after.

## The Arrival Log actually logs something, and the walkthrough loop closes on the Completion Report

Two gaps left open when Stage 5 was reported done, closed before Stage 6 started.

**The Arrival Log.** CLAUDE.md's own glossary defined it ("timestamped proof the worker was on the correct site at the start") and the stage rail has said "Stage 1 · on site" since `journey.ts` was written, but neither ever pointed at a real event. "On site" on the rail turned out to be a cosmetic read of `jobs.status = 'in_progress'`, nothing a worker ever did. This is why Stage 5.3's own brief could not build "worker on site today": there was nothing to fire it from.

`arrival_log` is one row per stage per Jamaica-local day, through `log_arrival()`, worker-only, same shape as `approve_stage`. Jamaica carries no daylight-saving shift, so a fixed UTC-5 read of "today" is exact rather than an approximation. A second tap the same stage, same day, is not an error, it is the same fact confirmed again: silently absorbed, no second notification. A new day on the same stage is a genuinely new fact and fires `worker_on_site` through the same `yaad-notify-client` infrastructure Stage 5.3 built. Verified live that a repeat tap does not double-notify, which was the one way this feature could have become spam rather than signal.

**The walkthrough's notes loop.** The FAQ's sentence was always "the notes are recorded, you confirm them in your portal, and both land on your Completion Report." Stage 5.5's original walkthrough work built the request and the call; this is what happens after. `walk_call_notes` is the worker's own write-up, kept separate from `walk_notes` (the client's pre-call request, a different question with a different answer) so a worker's account of the call never silently overwrites what was asked for. `record_walkthrough_notes()` refuses outright unless a call was actually confirmed (`walk_link is not null`), because there is no writing up a call that never happened. Editing after confirmation clears it, the same rule a fresh walkthrough request already applies to a stale link: a client's confirmation is worth exactly what it was given for, and a changed text is a new claim.

**A fourth notification kind, `walkthrough_notes_ready`, exists because the client is essentially never present when the write-up happens.** They were on the call; the notes get typed up after, when they are offline. Without a notification there was no way to know `record_walkthrough_notes()` had ever been called short of opening the job speculatively.

**Both land on the Completion Report, and only the confirmed loop counts.** An unconfirmed set of notes, or a walkthrough requested but never followed through, is not a record either side agreed to, and the static report at `/portal/jobs/[id]/completion` only renders the walkthrough section when `walk_notes_confirmed_at` is set. The `WalkthroughPanel` itself now stays visible on a completed job specifically when a walkthrough was in play (`signoff_method = 'walkthrough'`), so an unconfirmed set of notes is never stranded off-screen the moment `sync_job_status()` marks the job done; it simply stops offering a fresh request.

Verified against the live database and a real signed-in browser session for both roles: `log_arrival` refuses the wrong side and a stranger job id, is idempotent same-day, and correctly did not fire a second notification on the repeat call; `record_walkthrough_notes` refuses before any call is confirmed; `confirm_walkthrough_notes` refuses before notes exist; editing confirmed notes correctly re-opened confirmation and the client had to confirm again. Test job and both users deleted after.

## A third way to sign off a stage: in person (31 Aug 2026)

Founder's own framing: "if a client is in the country and can review the site by themself... they just confirmed completed job by in-person visual so that is signed out if there is any disputes in the future." A client physically in Jamaica does not need the same remote-evidence review as one four thousand miles away, and their own eyes on the property are worth recording as a stronger fact than a bare approval.

**This is an attestation, not a bypass.** Every rule `approve_stage()` already enforced stays exactly as strict: a dispute still blocks it, evidence still has to be filed for the stage before it can be approved. The client's tap is still the confirmation this repository's governing rule protects; nothing about who confirms, or what has to exist before they can, changed. What changed is that the tap now records HOW: `stage_approvals.confirmed_method`, `evidence` or `in_person`, set once, immutable, same as every other column on that table.

**A real bug caught before it shipped, not in this code but in how a signature change works.** The first draft of `approve_stage(p_job, p_method default 'evidence')` used `create or replace`, which does not retire the existing one-argument `approve_stage(p_job)`: Postgres treats a second parameter, even with a default, as a distinct function signature. Left alone, both would have existed at once, and a call passing only `p_job` (which is every existing caller) would have become genuinely ambiguous between the two rather than resolving cleanly. Fixed by dropping the one-argument version outright before creating the two-argument one, so exactly one `approve_stage` exists.

## WhatsApp evidence intake: a worker's photo lands on the job without opening the portal

Founder's own framing, 31 Aug 2026: a worker on site "has no time to log on and carry out those steps in the web... Uploading in the portal is fine but shouldn't be the first route." The portal upload from Stage 5.5 is not replaced. It is demoted from the only route to the fallback for the one thing WhatsApp genuinely cannot carry: a video bigger than WhatsApp's own 16MB client-side cap.

**Two research passes were wrong before this was designed, and both corrections changed the actual shape of the work.** First: `yaad-whatsapp-webhook` speaks to Meta's WhatsApp Cloud API directly, not Twilio, which everything else in this session's WhatsApp work uses. Second: nothing links a WhatsApp number to a worker. `jobs.worker_email` is the only identity a job carries for its worker; there was no `worker_phone` anywhere, on `jobs` or `worker_profiles`. Both had to be corrected before any code was written, and both are worth recording here because they are exactly the kind of assumption that looks obviously true until it is checked.

**`worker_profiles.phone` is the real column now, digits only, matched on the last 9 digits.** Same tolerance `findHistory()` already applies to a client's phone: WhatsApp's own "From" field arrives with inconsistent country-code prefixes, and pretending to E.164 precision nobody's numbers actually have would mean real matches missed, not fewer false ones caught. `link_worker_phone()` is the one door a worker has to set it themselves, same shape as `record_pay_info`, since `worker_profiles` carries no self-write RLS policy at all (admin write, signed-in read only).

**The trust model this repository already enforces for evidence is not loosened for this channel, it is reimplemented for it.** A WhatsApp message has no session, so it cannot lean on the RLS that already protects `evidence`: "this worker, this job, and no other." The check RLS would have made is made by hand instead, in `yaad-whatsapp-webhook`, before a single byte is trusted: the sender's phone must match a published (`active = true`) worker's linked number, and the job it lands on must be one that worker actually has open. The server-computed sha256 is unchanged from `evidence-actions.ts` and `yaad-evidence-video`, "computed HERE, on the server, from the exact bytes stored," now a third time in a third place, same rule.

**One active job, or more than one, decided the shape of the whole flow.** A worker with exactly one live job has their photo filed immediately, no question asked, because there is nothing to ask. A worker with more than one is asked which job, once, reusing `wa_intake_sessions`, the same table the guided client and worker-signup intakes already use for multi-turn state, given a third lane (`_lane: "evidence"`) rather than a new table. Media arriving while that question is still open is appended to the pending set rather than either lost or forcing an answer before the worker is ready; a burst of photos sent before a reply is the realistic case, not one photo followed immediately by an answer.

**Nothing is ever half-filed.** A photo is downloaded and staged into a neutral path (`_pending/...`, outside any job's own folder, since which job it belongs to is not always known yet) before anything is asked or decided. It only moves into the job's real folder, `{jobId}/...`, matching the same `storage.foldername(name)[1] = job.id` convention the evidence bucket's RLS policies already key on, at the moment a job is actually confirmed, whether that is immediately or after a worker answers which one. Verified live: when the underlying storage move genuinely fails (an object that was never really there), the function reports zero items filed rather than claiming success, and the session is still cleaned up regardless, so nothing is left half-answered.

**The portal deep link, not a paragraph telling a worker to go find it themselves.** For a video too big for WhatsApp to have carried in the first place, the confirmation message after a successful smaller upload carries a one-tap magic link straight to that job's evidence tab, already signed in, the same `generateLink` mechanism `yaad-portal-code` already uses. Founder's own wording: "so all they have to do is upload the file, nothing else."

**What could and could not be verified live, honestly.** Every piece of logic that does not require an actual Meta media fetch was proven against the running system: phone-to-worker matching, one-job-vs-many routing, the ordinal and fuzzy-title job-choice parser, session append-on-media, reprompt on an unrecognised answer, session cleanup on both success and failure, and an unrecognised phone number falling through to the exact pre-existing behaviour with no regression. `WHATSAPP_ACCESS_TOKEN` is confirmed unset on this project (found live, not assumed), so the one thing that could not be exercised is a real Meta media download and the real storage move that follows it. That needs a genuine WhatsApp message from a genuine device once Meta's Cloud API credentials exist, separately from the Twilio Trust Hub clearance confirmed the same day, which is a different provider for a different part of this product.

Closing the rest of what was queued after Stage 5: the reporting-agent WhatsApp digest, worker nudges, stall escalation to the founder, client delay notices, an admin stalled-jobs view, and the reliability log. Founder's own framing: "prompt to the workers ensuring he does this so the client is updated... if there is something that need escalating I will be contact direct."

**Money is untouched by all of it.** `approve_stage()` already refuses to release a stage with nothing filed against it; a stalled job simply never reaches that gate. **The reporting agent (`yaad/agents/reporting.py`) had existed since before this repository's live side did, fully built and fully guardrailed, and had never once run against a real notification.** Nothing in `supabase/functions/` or `web/` ever called it; confirmed by research before writing a line, not assumed. **The reliability log is the narrow version, not a computed score.** `worker_stall_history` is a plain read of `job_stall_state` joined to the job, one row per nudge, newest first. No aggregation, no ranking, no client-facing surface, nothing here feeds worker matching. Flagged against CLAUDE.md's own "Yaad Score computation" out-of-scope line before it was built, and built anyway once the founder confirmed she still wanted it, deliberately narrower than a score: a human reads a list and decides what it means, exactly as asked for.

**A real RLS bug, caught before it ever reached concierge, not after.** The first version of `worker_stall_history` was a plain Postgres view with no `security_invoker`, over a `job_stall_state` table that had been created with no RLS policy of its own at all. A plain view runs with the OWNER's privileges by default, not the querying role's, which means it would have exposed every worker's stall history to anyone PostgREST ever granted select to, regardless of whether they were an admin. Caught while wiring it into concierge, not after: `job_stall_state` now carries an explicit `is_admin()`-gated policy, the same gate every other staff-only table in this repository uses, and the view was recreated with `security_invoker = true` so it actually reads through that policy instead of bypassing it. Verified live, both directions: a genuinely non-admin authenticated user querying the view got zero rows while the underlying data provably existed; direct SQL confirmed the row was there the whole time.

**"Stalled jobs" in concierge follows the exact declarative pattern every other view in that file already uses** (`k`, `g`, `table`, `cols`, no `actions`, matching the read-only "Reviews" view precisely), rather than inventing a new rendering approach for one addition. Verified the file still parses: no console errors on load, and the whole inline script block passes `node --check` cleanly after the edit.

What could not be verified live: the actual Twilio send to a worker's phone and the actual ntfy push to the founder, since testing either would mean messaging a real person outside a purpose-built test account. Both reuse send functions copied line for line from `yaad-notify-client`'s own already-proven Twilio path (confirmed live and working the same day, Trust Hub cleared) and `yaad-vetting-upload`'s own already-proven `ntfy_topic` push, so the mechanism is the same one already carrying real traffic elsewhere in this product; only the specific recipients on this run were never real. Every SQL-level decision the cron function makes before reaching those two sends (which jobs qualify, at which threshold, whether already nudged or escalated, when the state clears) was proven directly against the live database.

## WhatsApp evidence intake moves to Twilio, same day it was built on Meta

The Meta Cloud API version shipped, verified, and correct, ran headfirst into Meta's own business verification, a process outside this repository's control and outside a reasonable evening's patience. Founder's own words: "i dont want to keep wasting my tokens on something that doesn't work... remove meta from this moving forward." The number already registered, already sending, already Trust Hub cleared, was sitting on Twilio the whole time. This moves the feature there instead.

**The Meta build was reverted cleanly, not left as dead code.** `yaad-whatsapp-webhook` is back to exactly its pre-evidence-intake state (`git show` against the commit before it, restored verbatim), rather than an unreachable branch nobody will ever configure sitting in a file that already does something else. Nothing about client intake or worker signup, which that file has always handled, changed at all.

**The new home is `yaad-inbound`, the multi-channel intake endpoint that already receives real Twilio WhatsApp traffic today.** This is a better fit than it first sounds: the header comment on that file has said since it was written, "WhatsApp keeps its own webhook because Meta's signature check and payload shape are its own problem. When it is approved it becomes one more row in the channel column, not a rebuild." Meta was never approved. Twilio, on the same channel, already was.

**The port is smaller than the original build, not larger, because so much of it already existed.** Twilio's signature verification (`twilioSigned`), its form-encoded parsing into a single `Inbound` shape, and its media download (`fetchMedia`, already proven in production for client-sent photos via `keepMedia`) needed no new code at all. What moved: `lookupWorkerByPhone`, `lookupActiveJobsForWorker`, `pickJobChoice`, `finalizeEvidenceItem` and `mintPortalUploadLink`, copied across unchanged, since none of them ever cared which messaging provider the bytes arrived from. What was rewritten: the media-staging step, since Twilio hands over a fetchable URL directly where Meta needed a two-step id lookup first, genuinely simpler than what it replaced. The reply mechanism changed shape too: Twilio's inbound webhook IS the reply channel (a TwiML response to the same request), where Meta needed a separate outbound API call for every message.

`wa_intake_sessions`, despite its name, was never Meta-specific: a plain `wa_id`-keyed table with a jsonb `answers` column, already carrying the "which lane is this conversation in" pattern (`_lane`) the client and worker-signup flows use. The evidence lane reuses it exactly as designed, no new table.

**What is proven and what genuinely is not, stated plainly rather than rounded up.** Every piece of logic that touches the database, phone-to-worker matching, active-job filtering, the job-choice parser, was verified directly against the live database with real data, the same discipline as every other piece of this session's work. What was not fired is a real, validly-signed Twilio webhook hitting this new routing: that requires `TWILIO_AUTH_TOKEN` to sign the request, which is a secret held by Twilio and this project, not by the person building it. The pieces that check that signature, parse the payload, and fetch the media are unchanged, already-live code already proving itself on every real client message this channel already receives; the new orchestration around them was written carefully against that same pattern, and its first real signed message is the genuine remaining proof, whenever one arrives.
